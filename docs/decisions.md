# 决策日志（decisions.md）

> 约定：涉及设计取舍的决定，先写进这里再动手。格式：日期 + 背景 + 选择 + 原因。面试官问"为什么这么设计"，答案都在这。

## 2026-08-19｜Go 切分微服务：按方案执行

- **背景**：方案技术栈表要求一个 Go 微服务来对齐 JD 的 Go 技能点；但 CLAUDE.md 的六大模块和 Docker Compose 服务数都没体现它，且文本切分本身用 Python 也能实现。
- **选择**：模块 2 就用 Go 实现切分服务（`chunker/`），Python 通过 HTTP 调用。
- **原因**：用户拍板严格按方案；Go 服务只做"纯文本切块"（无状态、约 100 行），PDF 文本提取等重活留在 Python 侧，既满足 JD 又不增加体重。交付时 Go 服务进 docker-compose。

## 2026-08-19｜版本控制策略：本地提交为主，GitHub 按里程碑推送

- **背景**：涉及"一次一功能、做完提交"的提交目标到底是本地仓库还是 GitHub。
- **选择**：本地仓库 D:\agenthub 是唯一提交点（每功能 commit 一次）；GitHub 按里程碑（每模块验收通过或每天结束时）推送。
- **原因**：本地 commit 已完整保留历史（面试加分）；GitHub 国内网络不稳定，每小步都推浪费时间为风险高；里程碑推送兼顾备份与展示。

## 2026-08-19｜会话双层存储：元数据落 MySQL、消息落 Redis

- **背景**：方案只说"会话历史存 Redis（TTL）"，没说会话列表/统计存哪。
- **选择**：MySQL 建 sessions 表只存元数据（session_id/agent_id/标题/条数/时间），消息内容存 Redis 并设 TTL。
- **原因**：Redis 天然适合"多轮上下文 + 过期"；但列表/统计/审计需要持久化元数据，MySQL 是本职。两层各取所长。

## 2026-08-19｜检索可插拔：use_rag 开关

- **背景**：架构图里编排层含"检索"，但模块 3 的验收只是"拿到大模型回答"，知识库/双路检索要到模块 2/6 才完成。
- **选择**：agents.use_rag 字段开关，模块 3 先纯 LLM 跑通；检索/工具随模块进度逐步接入，不做大重构。
- **原因**：每步都可验收、可回滚；编排通道从第一天就预留插槽，避免后期返工。

## 2026-08-19｜模块 2 入库先只写 Chroma，ES 索引到模块 6 再建

- **背景**：方案把 ES 放模块 6，但没写明模块 2 入库时要不要同步建 ES 索引。
- **选择**：模块 2-5 只走向量单路；模块 6 才装 ES 并回填索引。
- **原因**：8GB 机器上 ES 是内存大户，提前白养一份没被使用的索引浪费资源；收敛范围，按功能模块交付。

## 2026-08-19｜不引入 Alembic 等重量级迁移工具

- **背景**：建表需要迁移方案。
- **选择**：开发期用 SQLAlchemy `create_all` 建表；确有结构调整时手写迁移脚本；不引入 Alembic。
- **原因**：单机开发、表只有 6 张，引入迁移框架是过度设计；面试讲"为什么不用 Alembic"反而加分（范围收敛意识）。

## 2026-08-19｜新增"原生 HTML+JS 控制台"前端（对原方案"无正式前端"的修订）

- **背景**：纯后端 + Swagger 只能点 JSON，用户（求职者）反馈"真实交互下来才有意思，光后端感受不到每个功能"。原方案把"正式前端"列为明确不做。
- **选择**：新增一个**零依赖**的网页控制台（`web/`，vanilla HTML/CSS/JS + fetch 调 REST API），由 FastAPI 用 StaticFiles 直接托管（`/ui`）。不装 node、不引框架、不加内存。控制台随模块逐步生长：当前 Agent 管理页签 → 后续知识库/对话/日志页签。
- **原因**：满足"真实交互"诉求的同时守住 8GB 机器 + 不引入重框架的底线；手写 fetch 对面试反而是加分点（能讲清每一行）。Streamlit 演示页保留在收尾阶段（截图/录 GIF 用），不与之冲突。

## 2026-08-19｜Agent 服务层直接返回响应模型（AgentOut），而非 ORM 对象

- **背景**：模块 1 实现中发现，FastAPI 用 `from_attributes` 序列化 ORM 对象时，`knowledge_base_ids`（由绑定关系算出）不存在于 ORM 属性上，触发 ResponseValidationError。
- **选择**：service 层所有对外函数在 session 仍打开时就把 ORM 物化为 `AgentOut` 再返回；API 层保持薄壳。
- **原因**：避免"session 已关闭后再懒加载"的坑；返回类型清晰，后续模块（对话）复用也安全。

## 2026-08-19｜API Key 安全策略（两层防线）

- **背景**：项目要上 GitHub 公开展示，但百炼 API Key 一旦泄露会被盗刷。
- **选择**：真实 Key 只存在本地 `.env`（.gitignore 忽略）；仓库只提交 `.env.example` 占位；git 层配 pre-commit/pre-push 钩子拦截 `.env` 入库（含 `git add -f` 强行走走 case）；将来首次公开前在控制台轮换 Key。
- **原因**：密钥永不进版本历史；钩子兜底防手滑；轮换兜底防对话记录泄露。输送环境变量进 docker-compose 时用 `${DASHSCOPE_API_KEY}` 透传。
